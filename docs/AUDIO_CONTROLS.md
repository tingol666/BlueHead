# 音量、实时码率与麦克风发送

## 音量路径

每台移动设备有“播放”和“麦克风发送”两个音量按钮，点击后展开滑块、静音与恢复 100%，设置随配对身份保存，范围均为 0%–200%。

- 设备声音 → 电脑：同时调节此设备的媒体、通话下行。
- 语音发送 → 此设备：调节发送给此设备的混合声音；无通话时可预先设置。

首页总控也是 0%–200%：设备声音播放总量、实体麦克风采集量、电脑播放声音发送到移动设备的音量。后两路先混合，再应用当前设备的上行音量。关闭电脑混合时只显示两个总控，打开后显示第三个。第三个总控不会改变电脑本身正在播放的声音，只影响发送给移动设备的部分。

每个音量弹层均有独立静音按钮，取消静音恢复该控件静音前的数值；0% 静音，100% 为单位增益，200% 为两倍幅度。峰值超过数字范围时限幅，避免数字削波；不能修复信源已有的失真。“暂停发送到设备”停止向移动设备发送后两路声音，电脑仍能播放设备声音。

## 高级混合

在 **首页 → 混入电脑声音** 开启；二级高级设置保留说明。默认关闭，可在使用麦克风期间开关。保持原有麦克风选择与蓝牙连接。若电脑声音采集失败，提示原因并保留实体麦克风路径。

原生模块使用 WASAPI 进程排除模式，排除 BlueHead 后台工作进程及其子进程所渲染的声音。其他电脑应用的播放声音可混入发送给移动设备的麦克风声音，BlueHead 接收的移动设备声音不会被数字返送。此接口不依附一个物理输出端点。需要 Windows build 20348 及以上。依据：[Microsoft Application Loopback](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)。

这是数字音频排除，不是声学回声消除。使用扬声器时，实体麦克风仍可能从空气中拾到通话外放声；耳机可以避免这条声学回路。电脑播放声音只在移动设备启用蓝牙麦克风期间采集，不保存录音文件。

## 实时数据

设备卡片每秒刷新，码率取最近两秒实际编码负载，停止音频后回落到零。例如：

```text
A2DP / aptX HD · 48 kHz · 576 kb/s
HFP / mSBC · 16 kHz · ↓ 60.8 kb/s  ↑ 60.8 kb/s
```

实际值可能波动，示例不是硬编码的显示值。媒体去掉 RTP 和媒体封装；mSBC 去掉 H2 头，CVSD 将主机 PCM 统计换算为语音负载。数值不包含蓝牙重传、物理层开销，也不代表解码后的 PCM 码率。Windows 共用蓝牙方式无法取得这层统计，明确显示由系统管理。

点击卡片“详情”可查看包速率、待播放缓冲和已重同步次数；通话显示收包计数、麦克风及电脑声音状态。通话和媒体共用同一条协议/频率/码率显示，不另建通话卡片。

## 挂断后的 InvalidDataError

有些手机挂断后继续使用原编码器，恢复点可能落在 aptX/HD 的任意奇偶同步相位。旧版遇错就重置，下一包未必是新编码器起点，可能再次报错。新版检查真实码字的两轮同步周期，再从正确边界重建解码状态，不通过删除错误文字来掩盖问题。持续无法恢复仍有明确提示；短暂恢复计入设备统计。

本机同一组错相位压缩数据：Beta 3 出现 3 次 InvalidDataError；Beta 4 无异常抛出并完成自动恢复。自动检查另覆盖丢包后的再次恢复。Beta 4 已获本机用户确认：挂断后媒体恢复、双向通话、热切换正常，无 InvalidDataError；高级混合正常、无数字返送。0.2.0 保留该音频实现。

本机高级上行验证经过实际采集、重采样、增益和 mSBC 编码，200%/100% 幅度比约 2.00，0% 为零；每设备 50% 可抵消总控 200%。输入输出切换及三次本机流重建保留语音链路。具体报告随版本 Release 提供；这些不是端到端延迟测量或全部手机的兼容保证。

冻结后台可只检查电脑声音模块的实际加载与打开/关闭，无蓝牙操作：

```powershell
app\engine\BlueHead.Engine.exe --system-audio-check C:\Temp\BlueHead-system-audio.json
```

## 录音与录像中的蓝牙麦克风

麦克风通道不限于电话。BlueHead 收到对端 SCO/eSCO 请求时建立语音链路，不要求 HFP CALL/CALL_SETUP 指示为通话中；音量、静音、电脑声音混合与设备热切换也作用于这条链路。界面使用“电脑麦克风”“发送到设备”和“语音通道”等通用名称，避免把录音错误显示为正在打电话。

Android 的录音、相机或视频应用需要支持并选择蓝牙麦克风。Windows 端无法强制接管移动端应用的输入源。Android 官方说明 SCO 可在非通话场景建立，较新应用使用音频设备路由接口；参考 [AudioManager.startBluetoothSco](https://developer.android.com/reference/android/media/AudioManager#startBluetoothSco()) 与 [AudioRecord.setPreferredDevice](https://developer.android.com/reference/android/media/AudioRecord#setPreferredDevice(android.media.AudioDeviceInfo))。

当前麦克风链路仍为 HFP：CVSD 8 kHz 或 mSBC 16 kHz 单声道，以实际协商为准；媒体的 AAC、aptX HD 或 LDAC 码率不等于录音输入质量。已追加没有电话指示、静音下行时仍可发送实体麦克风的 CVSD/mSBC 自动回归。具体移动端录音、相机应用还需实测，不把通话验收当作录音录像兼容验收。

## 多设备与码率选择（0.2.1）

同一 AX211 与两台移动设备对照：双 aptX HD 48 kHz 时，一路频繁重同步，另一条保持约 48k 解码帧/s；请求切换中心角色被对端拒绝，没有改善。同一组设备使用双 AAC 后，用户确认两路稳定，计数中两路均约 47,926 帧/s，未出现同步错误。软件中双 aptX HD 解码与原生混音也能保留两路信号。因此结论限定为该组合的双高码率无线链路不稳，不是控制器不能接收两路声音，也不把某个蓝牙版本当作并发带宽保证。

自动模式优先提供可用高清编码，同时提供 AAC 与 SBC 供协商；手动高清编码不被后台偷偷改写。首页可选 AAC 192 kb/s 协商上限，更低码率要重新协商，因而通过明确按钮停止接收再重新开启，保留配对和设置。0.2.1 的出声方式位于二级设置；1.2.2 已移到首页与编码同一行。单设备模式通过 AVDTP Suspend 请求其他媒体暂停，本机独立门控保证未选声音不会碎片式混入；对端不响应时提示用户手动暂停。

竞争媒体在连续两个约半秒窗口严重缺帧，并伴随丢包／同步错误，或持续严重供给不足时触发隔离。解码继续以监测恢复，连续三个干净窗口后解除；本机淡入淡出约 10 ms。计数仅反映应用收到的 RTP，不含控制器内重传。门控不修改 0%–200% 用户增益，不作用于 HFP 语音输入或麦克风上行。

## 0.2.1 最终真机验收

2026-10-25，用户使用日常安装位置的最终 0.2.1 绿色包确认：双 AAC 同时播放稳定，单／多设备出声切换正常；微信双向语音、电脑播放设备与麦克风热切换、挂断后媒体恢复均正常。本次验收对应新发布包，区别于此前诊断接收器的 AAC 对照。AAC 192 kb/s 实际协商未单独明确确认；不扩展为其他手机、控制器或编码组合的兼容承诺。


## 自动接替（1.2.2）

首页选择“单设备自动接替”。当前来源明确暂停后约 0.1–0.2 秒、无音频包约 0.8 秒时，从仍连接且已请求播放的等待来源中选择最近请求者，请求恢复其 AVDTP 媒体流。控制器、移动端播放器响应和缓冲仍会影响实际听到声音的时间。判断使用包活动，不使用声音幅度；安静段落不会误切换。

本应用为了单设备策略而暂停的来源保留等待资格；远端主动暂停、关闭或断开会移除其等待资格。没有等待者时保留当前媒体门控，避免某些播放器不重新发送 START、直接恢复 RTP 后仍无声。语音链路占用与结束后的短暂恢复期优先，自动接替不抢占麦克风。模式和主动选择通过同一个异步锁串行，避免相互交错。

新增自动检查通过真实 AVDTP 信令及接替后的 SBC 解码 PCM，覆盖主动暂停、无包、语音优先与结束宽限、无候选者、远端取消及旧回调身份隔离。2026-10-25，用户使用最终 1.2.2 绿色包确认：A→B、B→A 两次自动接替均正常，无碎音或来回切换；微信双向语音、播放设备与麦克风热切换、挂断后媒体恢复三项均正常。该验收与历史 0.2.1 结果分别记录，不扩展为所有设备或编码的兼容承诺。
