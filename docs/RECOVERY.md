# 音频异常恢复

本策略在 2.1.1 实现。目标是隔离故障、保留正常方向和音质，再平滑恢复到新鲜音频。不会通过降低媒体编码、采样率或持续扩大缓冲来隐藏错误。

## 各类故障分别处理

| 条件 | 处理 | 自动重试 |
| --- | --- | --- |
| 已结束的来源、过期 lease／epoch、取消或被新请求替代的切换 | 丢弃旧请求，不影响新来源；不计为设备故障 | 无须重试 |
| 单个坏包、重复包、乱序包 | 对应流的编解码／连续性层处理；不清空整条音频链 | 保留解码历史 |
| 连续 8 次无有效输出的解码失败 | 只修复该来源的解码状态；保留仍有效的 PCM、累计位置及兼容配置，修复接缝交给实际播放消费者；其他设备与方向继续 | 1–8 秒退避 |
| 压缩包处理时已过期 | 入队后、解码后各检查一次；媒体 180 ms、语音 90 ms；过期结果不进入 PCM | 首个新鲜包重建接收状态一次 |
| 播放／麦克风端点消失或暂时忙、超时 | 唯一音频设备控制线程准备候选；保留可用旧路由；指定端点消失可回退默认，返回后恢复原选择 | 0.5、1、2、4、8 秒，最大 8 秒 |
| 权限拒绝、不支持的格式／采集方式 | 给出具体原因，等待权限或设置变化 | 不自动反复打开 |
| 内存／资源不足 | 保留可用方向，避免反复分配造成进一步压力 | 10–30 秒 |
| 未分类的内部打开错误 | 分类与原生错误码保留；连续 3 次后要求人工检查 | 有限退避，随后停止自动重试 |
| USB 拔出、提交失败、传输失败、控制通道积压 | 分开报告原因，结束该传输会话 | 不在音频回调中重建 USB／HCI 所有者 |
| 系统设备调用超时失去进展 | 原生进程的控制期限／退出边界限制影响 | 不在同一进程另开竞争所有者 |

设备重新打开后必须持续健康 5 秒才清除失败历史，防止“打开即失败”的重试风暴。后台刷新不绕过退避；用户主动刷新可重试。失败的新设备选择不会虚假显示为切换成功，仍可用的旧设备继续工作。

麦克风格式切换的内存、滤波系数及私有设备准备不持有公共 PCM 桥接锁。新方案提交前验证来源／路由修订号及当前任务；繁忙时退出锁再重试，取消或准备失败保留旧输入。旧设备关闭、转换方案销毁及 JSON 状态记录不进入桥接提交临界区。麦克风切换不能因准备耗时而阻塞另一条电脑声音输入。

## 接收会话、控制后台与断连边界

停止接收分为“撤销当前会话”和“完成资源退役”。开始停止时立即撤销界面中的设备、语音、混音和待完成请求；此时显示“正在停止”，不会提前显示可以重新开始。HFP、AVRCP、媒体工作线程和音频端点先退役，之后才关闭唯一 USB/HCI 传输。对端连接并行断开，单个对端最多等待 2 秒，避免设备数量把等待时间逐项叠加。`asyncio.run` 中已取消但仍在执行的控制操作退出后，才发送最终 `stopped`。

原生端点控制保留 12 秒系统调用看门狗；原生应用的停止总期限为 20 秒，界面另有 25 秒最后退出边界。它们限制的是异常清理耗时，不改变正常音频缓冲、编码协商或播放延迟。旧的应用级 5 秒期限可能早于正常语音和多连接退役完成，现已移除这一冲突。重复停止不会延长总期限。

控制后台需先完成版本握手；界面每 2 秒向 Python 控制循环发送一次轻量心跳，15 秒未响应判为控制失去进展。心跳不走音频回调，也不查询音频设备或逐次写入运行日志。进程退出、输出管道失效和心跳超时分别检测；即使子进程仍持有输出管道，主后台退出也不会被漏掉。恢复由用户点击“开始接收”触发，先终止并确认旧进程作业已空，再创建一个新后台，不自动无限重启。

身份边界包括后台代次、实际 ACL 连接对象、HFP 协议对象、原生媒体租约和语音 epoch。旧设备事件、旧控制会话的音量／来电事件、旧麦克风或电脑声音采集请求的结果都不能修改新会话。主 ACL 断开时，控制器层立即撤销它的 SCO 子链路，不依赖另一个语音断开事件一定到达；控制层同时退役对应语音资源。成功连接事件复用控制器句柄时，先撤销旧原生路由，防止新语音包被上一个会话的编码器状态接收。

物理断连通知不能被一个解码器或端点清理错误打断，否则同一连接上的其他协议监听器会漏掉断连。界面还根据声明完整的设备快照校正残留或缺失的设备卡片；Windows 共用接收的局部快照不会被误当成完整列表。没有音频数据只表示暂停或空闲，不据此伪造蓝牙断开。

## 音质与时间边界

媒体／语音工作线程是包缺口补偿的唯一所有者；渲染回调仅做有界的末端淡出／恢复衔接，不进行第二次周期搜索。发生长停顿时只舍弃已经错过播放期限的数据，避免恢复后播放积压的旧语音。经典发送队列以编码开始时刻检验 90 ms 期限；未提交的过期帧不再发送，已经部分提交的同一帧只完成其尾部，不拼入另一帧。普通短缺口不会重开解码器或重复预缓冲。

解码器修复与暂停、SSRC／配置改变、过期来源及断连的硬退役分开。修复不得清空仍可播放的真实 PCM，也不能重复记账已经补过或省略的缺口。修复后的第一个真实样本携带同一 PCM 游标发布的标记；消费者依据实际听得到的前驱进行约 1 ms 的有限衔接，已静音或已有缺口恢复窗口时不再叠加。普通不确定性标记不改变正常 PCM。硬退役的逻辑读取下界只能前进；物理槽位复用仍等待旧回调离开，避免把旧声音重新纳入新来源或覆盖在途读取。

AAC 恢复使用 `avcodec_flush_buffers` 清除旧 MDCT 重叠，保留 LATM 配置，因此后续 `useSameStreamMux` 包无需重新携带配置。测试先证明旧实现会将约 0.398 峰值的旧声音带入静音帧，再确认清理后的静音残留低于 1e-8、后续音乐仍正常。该 API 的用途见 [FFmpeg 文档](https://ffmpeg.org/doxygen/trunk/group__lavc__misc.html)。实际行为同时按仓库固定的 FFmpeg 源码与二进制检查。

语音接收恢复不重置发射编码器或 H2 序号。CVSD 字节缺口保留 PCM 字边界奇偶信息，避免丢掉奇数字节后整段错位。挂断会先停止语音消费者，再清空并释放输入槽；旧回调不能写进重用槽位。

float 音频一路保留到必要的编码边界；非有限数和明显越界的损坏样本在污染滤波器历史前隔离。实时线程局部启用 FTZ／DAZ，避免接近绝对静音的非规格化浮点数触发耗时尖峰；正常 float 低电平仍保留，调用者的浮点环境完整恢复。未启用 fast-math。

## 生命周期与用户状态

控制接口返回类别、原生码、是否可重试和旧路由是否仍可用。UI 合并同类提示，短暂的一次恢复不反复刷屏；恢复提示只清除它自己的警告，不覆盖其他错误。诊断只记录数值、分类和计数，不采集声音。

所有资源回收都尽力执行，第一次失败被保留；回收异常不能掩盖最初导致退出的错误。已取消的媒体监视任务属于正常关闭，不等同设备故障。读取统计不参与实时线程的锁和设备生命周期。

## 软件验证

自动测试使用生产 DLL／原生进程的同一条控制、队列和编解码路径。离线模式在执行设备准备的最内层拒绝真实设备打开；测试库存与错误码注入不能进入发布运行模式。

覆盖：错误分类与退避、失败候选保留旧路由、最新切换优先、端点回退和返回、后台刷新不强制重试、挂断与旧会话竞态、接收重置不影响发射、CVSD 奇数缺口、解码后超时、原生线程阻塞、非有限样本、非规格化浮点耗时、原始异常保留及逐项资源回收。

最终检查记录在本地 `work/recovery-complete.xml`、`work/clock-recovery-complete.json`、`work/recovery-complete-soak.json`。这些是软件检查，不作为无线环境和移动设备听测的替代。每次发布的实际汇总和文件摘要另见同版本 `VALIDATION.md`。

本阶段完成时的实际结果：全量 675 项通过，Ruff 通过，桌面 116 项检查通过；2 小时虚拟时钟在 ±500 ppm 下无欠载／丢弃，立体声相位误差为零。120 秒 AAC＋LC3 双工回放注入 181 次丢包、±3 ms 抖动及多次 2 秒 GIL 阻塞，无解码错误、压缩队列丢弃、PCM 丢弃或欠载，预热后整零片段为零。八路 480 帧回调中位数正常信号 52.3 μs、非规格化信号 52.6 μs，均不在回调中搜索周期；这包含测量调用开销，不是端到端延迟。

## 蓝牙冷启动与系统恢复

2.1.2 区分 WinUSB 可访问、Intel 引导模式、固件已运行、原厂驱动已绑定和 Windows 无线电就绪。固件缺失、损坏、未适配、签名拒绝和超时保留原始原因；停止可取消。系统蓝牙恢复若已绑定原厂驱动但仍无法完成初始化，记录并提示“驱动恢复完成，请重启电脑”。驱动绑定失败不写成恢复成功，详见 [FIRMWARE.md](FIRMWARE.md)。

2.1.2 对 LDAC 补齐了 RTP 缺口与有限恢复窗口，并统一高采样率诊断单位；源码中的逐样本对照与实际结果见 [AUDIO_FIDELITY.md](AUDIO_FIDELITY.md)。PLC 归属仍在来源工作线程，输出回调不增加周期搜索。

## 控制器失去响应与用户确认恢复

运行中的 HCI Hardware Error、已识别的厂商异常复位、初始化命令无响应和控制器连接表失配分别保留故障类别。USB 拔出、软件回调失败和后台通信错误不会被写成同一种硬件故障。现有 HCI 命令队列低频检查控制器与活动连接；两次确认同一个当前句柄不存在，才撤销失效会话。暂停媒体不作为断连依据，Python 调度阻塞不消耗控制器响应等待预算。这些检查不创建第二个 USB/HCI 所有者。

发生故障时立即撤销无效设备卡片，并等待旧会话完整退出。页面显示明确的处理入口；不会在来电、录音或后台异常时自动弹出管理员授权。用户打开“蓝牙驱动设置”并在页底右侧点击“修复专用蓝牙”后，才通过已保留的原厂驱动初始化所选适配器，再切回专用接收。完成后留在设置页，由用户回首页点击“开始接收”。固件获取、驱动切换和返回首页均不自动启动接收。

取消授权后保留恢复按钮。恢复失败保留具体诊断；原厂驱动已绑定但仍需重启时提示“驱动恢复完成，请重启电脑”。缺少有效备份或适配器身份不明确时，不进行不确定的驱动交接。

蓝牙驱动设置按电脑蓝牙设备、蓝牙使用方式、真实驱动状态组织。Windows 共用对应基础功能，BlueHead 专用对应进阶功能。当前状态、重要影响与操作固定在页底，按钮集中靠右。选择与驱动不匹配的模式只提出待完成的切换，选框保持原有效模式；驱动操作成功后才应用，离开页面或取消即放弃。设置和恢复均不自动开始接收。基础模式明确标注电脑端 Windows 配对、返回 BlueHead 点击“开始接收”、设备端播放三个步骤；只有缺少启动文件时才显示对应工具。

## 多设备语音保护

“设置 → 通话／语音保护”默认开启，停止接收后可保存修改，旧配置缺少此字段时仍默认开启。保护针对所有当前支持的 HFP 麦克风语音连接（CVSD、mSBC、LC3-SWB），不根据通话、录音或录像应用名称，也不根据之前的媒体编码或播放模式推断。因此 AAC、SBC、LDAC 等媒体来源使用相同准入策略。语音编码切换或协商失败不会提前解除仍在使用中的语音保护。

在回复 AT+BCS 和接受同步语音请求之前，保留请求使用麦克风的 ACL，等待其它 ACL 完成断开。最多等待两秒；若未完成，不继续建立冲突语音链路，显示断开其它设备后重试。已有媒体编码、增益、缓冲和原生音频算法均不改变。正在进入或使用语音时，新 ACL 请求在 HCI Accept 之前被拒绝；已在途的连接也会先退役，不只隐藏设备卡片。首页持续显示原因，并对重复的自动重连提示限流。

保护按实际连接对象和语音链路身份释放，旧断连事件不能解除新语音的保护。语音结束、连接丢失、协商失败或接收停止后解除限制；没有语音链路建立的预留会超时释放。解除后允许设备重新连接，不主动重连或自动恢复对端播放。

首页使用“蓝牙使用方式”标明所选管理方式。选择需要改驱动的方式后，立即显示待确认的目标和页底操作；只有显式点击操作才会请求管理员授权，随后显示实际处理进度。启用专用驱动的断连影响用红色提示，恢复 Windows 的说明则介绍系统蓝牙恢复与失去专用功能的区别。四个说明入口以分节卡片按需展开；多设备播放卡片显示已保存连接上限及当前连接数。系统托盘左键单击显示并恢复主窗口，右键保留菜单操作。
